## What you will learn

## Understand the idea

A transition interpolates a property when its computed value changes. Specify the property, duration, and timing function. Avoid transition:all: a future layout change could unexpectedly animate too. Put transition on the base state so entering and leaving the state behave consistently.

Transforms can move or scale a visual box without reflowing surrounding content. That can be efficient, but it also means moved content may overlap neighbours. Keep the effect small and test it. A transform does not change reading order or semantics.

Prefer no motion by default, then enable a nonessential effect only when prefers-reduced-motion:no-preference matches. Reduced motion must not hide content or remove functionality. Keyboard users should receive clear state feedback even when movement is disabled.

## Worked example

### HTML body

```html
<h1>Project link</h1>
<a class="project-link" href="#project">Explore my portfolio</a><section id="project"><h2>Portfolio notes</h2><p>The link leads here.</p></section>
```

### styles.css

```css
.project-link { display: inline-block; padding: 1rem; border: 2px solid currentColor; }
.project-link:focus-visible { outline: 3px solid #174ea6; outline-offset: 4px; }
@media (prefers-reduced-motion: no-preference) {
  .project-link { transition: transform 160ms ease-out; }
  .project-link:hover, .project-link:focus-visible { transform: translateY(-2px); }
}
```

## Try it and observe

Test hover and keyboard focus. Emulate prefers-reduced-motion:reduce in DevTools; the link should still work and have an outline, but should not move.

## Practice challenge

Use a 120ms transition and a 1px upward movement. Preserve no movement under reduced motion and retain the keyboard outline.

Save your changes, reload, and compare the observed result with your prediction. Keep a short note of what changed and why.

<Accordion title="Need a hint?">

Keep transform and transition inside the no-preference query, not the focus outline.

</Accordion>
