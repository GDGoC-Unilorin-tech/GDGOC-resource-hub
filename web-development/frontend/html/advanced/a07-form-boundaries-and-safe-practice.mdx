## HTML stops at a boundary

A browser can collect values, check some constraints, and send a request. A server or service must receive, validate, authorise, and process that request. The static results page in this course does not send email or store messages.

GET is appropriate for retrieval with shareable query parameters. POST commonly submits changes, but does not encrypt data by itself. HTTPS protects transport; server handling and storage still require appropriate controls. Password inputs only obscure their visible characters.

## File uploads

A real file-upload form normally uses POST and `enctype="multipart/form-data"`. The file input's accept attribute is a selection hint, not security validation. A server must validate file content, size, permissions, and storage. No upload endpoint is provided here.

Use the following as a reading example, not a form you should submit. The destination is illustrative.

## Worked example

```html
<!-- Reading example only: /upload is not implemented -->
<form action="/upload" method="post" enctype="multipart/form-data">
  <label for="work">Project file</label>
  <input id="work" name="work" type="file" accept=".html" required>
  <button type="submit">Upload project</button>
</form>
```

The markup expresses request intent. It does not supply authentication, file validation, storage, or an upload service.

<Note>A field marked required can be bypassed. Never trust browser checks as your only validation.</Note>

## Check your understanding

Does POST encrypt a submission? Does `accept=".html"` guarantee a safe uploaded HTML file?

Write your answer before opening the explanation.

<Accordion title="Check your answer">

POST chooses a request method, not encryption. HTTPS protects transport. Accept is a file-selection hint, not proof of content or safety; a receiving service must validate files and handle storage and delivery appropriately.
